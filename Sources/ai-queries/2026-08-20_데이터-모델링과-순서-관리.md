## Q&A 원문

### Q1. natural id 가 뭐더라

**A.** Natural ID(자연키)는 **업무적으로 이미 의미가 있고, 그 자체로 행을 유일하게 식별하는 값**이다. 시스템이 생성한 값이 아니라 현실 세계에 이미 존재하는 식별자.

| 구분 | Natural Key | Surrogate Key |
|------|-------------|---------------|
| 출처 | 업무 도메인 | 시스템 생성 |
| 예시 | 사업자등록번호, ISBN, 이메일, `invoice_no` | `AUTO_INCREMENT`, UUID |
| 의미 | 있음 | 없음 |
| 변경 | **바뀔 수 있음** | 절대 안 바뀜 |

PK로 자연키를 쓰지 않는 이유: 자연키는 바뀐다. 주민번호 체계 개정, 사용자의 이메일 변경 등. PK가 바뀌면 FK로 참조하는 모든 테이블이 연쇄로 깨진다.

실무 정석: **PK는 surrogate, natural key는 UNIQUE 제약으로 별도 보장.**

Hibernate `@NaturalId`의 실익:
1. 2차 캐시 활용 — `byNaturalId()` 조회는 자연키→PK 매핑이 캐시됨
2. `mutable = false`로 불변성 강제
3. "이 컬럼이 엔티티의 업무적 정체성"이라는 의도 문서화

정산 도메인 적용: SAP 전표(`전표번호+회계연도+회사코드`), Invoice(`invoice_no`), Zuora 연동 개체(`zuora_id`). **외부 시스템 발급 ID는 전형적인 natural id** — PK로 쓰지 말고 내부 PK 따로 두고 UNIQUE로 보장.

### Q2. 회원(Member)은 강사(Instructor)가 될 수도 있다. `1 ---- 0..1` 로 관계를 맺고 있는데, 강사가 되려면 회원이 필수 조건이면 필수이기 때문에 1:1로 봐야 하는 거 아니야?

**A.** `1 ---- 0..1`은 **이미 1:1 관계이고**, "강사가 되려면 회원 필수"도 이 표기가 이미 담고 있다. 모순 없음.

카디널리티 표기는 **두 가지 정보를 동시에** 담는다:

| 축 | 읽는 값 | 결정하는 것 |
|---|---|---|
| 최대 카디널리티 | `1` vs `N` | 관계의 **유형** (1:1 / 1:N / N:M) |
| 최소 카디널리티 | `0` vs `1` | 참여의 **필수/선택** |

UML은 **반대편 끝에 붙은 숫자**를 읽는다:
- Instructor → Member 방향: "강사 한 명은 회원 정확히 1명" → `1` ← **이게 '회원 필수 조건'**
- Member → Instructor 방향: "회원 한 명은 강사일 수도(1) 아닐 수도(0)" → `0..1`

만약 `1 ---- 1`이면 "모든 회원이 반드시 강사"가 된다. 그러면 테이블을 나눌 이유가 없다. **개체를 나눈 것 자체가 "강사가 아닌 회원이 존재한다"는 선언.**

구현: FK를 **필수(`1`)인 쪽, 즉 Instructor**에 둔다. `member_id`를 Instructor의 PK 겸 FK로 쓰면 한 줄의 PK 선언이 `1 ---- 0..1` 전부를 표현한다.

**사용자 최종 이해**: "멤버 쪽에서 보면 모든 멤버가 강사는 아니니까 0일 수도 1일 수도 있다는 표현이었구나."

> [!important] 카디널리티 읽는 규칙
> "내가 선 쪽 개체 **하나**를 기준으로, 반대편 개체가 **몇 개** 붙는가" — 그 답을 **반대편 끝**에 적는다.
> 카디널리티는 "전체 집합의 통계"가 아니라 **"인스턴스 하나의 시점"**이다. "회원 1만 명 중 강사 50명"이라는 비율은 다이어그램에 안 담긴다.

### Q3. 커리큘럼 밑에 수업 5개(순서 1~5). 5번째를 드래그해서 2와 3 사이에 놓으면 1,2,5,3,4가 된다. 이 로직을 어떻게 만들까? 보편적인 접근방법이 있다면 바로 답을 내지 말고 내가 답을 맞출 수 있도록 유도해줘. 일단 내가 생각해본 방안들을 리뷰해줘.

#### 사용자가 스스로 제시한 3가지 방안

1. **링크드 리스트** — prev/next 저장. 단 "3,4,5가 연쇄 업데이트될 것 같아 아닌 것 같다"
2. **전체 재작성** — 커리큘럼당 최대 100개니까 FE에서 정렬된 ID 배열을 받아 전체 UPDATE
3. **희소 배치** — 10000, 20000, 30000...으로 벌려놓고 삽입 시 두 이웃의 평균값. 단 "반씩 깎으면 이진트리처럼 줄어 금방 고갈될 것 같다"

#### 방안별 리뷰

**방안 1 — 전제가 틀렸음.** 링크드 리스트에서 5를 2와 3 사이로 옮기면 `2.next`, `5.next`, `4.next` **3행만** 바뀐다. 연쇄 업데이트는 없다. O(1). "3,4,5가 연쇄로 밀린다"는 **배열 사고**이고, 링크드 리스트는 정확히 그 비용을 없애려고 만들어진 자료구조다.

다만 RDB에서 쓸 때의 진짜 문제:

| 문제 | 내용 |
|---|---|
| 정렬 쿼리 불가 | `ORDER BY`로 순서를 못 뽑음. 재귀 CTE 또는 앱 메모리 연결 필요 |
| 페이징 불가 | `LIMIT/OFFSET` 불가 |
| 체인 파손 치명적 | 포인터 하나만 틀려도 목록 전체 붕괴, 사이클 위험 |
| 동시성 | 동시 드래그 시 사이클/고아 노드 |

**방안 2 — 가장 저평가되고 있었음.** 100개 규모에서는 사실상 정답. 불변식(`1..N` 연속 정수)이 항상 성립하고, 디버깅이 자명하며, 어떤 이동이든 동일 코드 경로. 단점은 FE 신뢰 필요(서버 검증 필수)와 동시 편집 시 lost update.

**방안 3 — 문제의 핵심을 정확히 찾아냄.** 간격 10000이면 `log2(10000) ≈ 13`회 만에 고갈. 간격을 10억으로 해도 30회. 지수적으로 완화될 뿐 **원리적으로 유한**. 사용자의 직관("금방 동이 날 것 같다", "20001 다음엔 에러") 둘 다 정확.

> [!warning] 사실 정정
> 사용자가 "sr을 **내림차순** order by 하면 1,2,5,3,4"라고 했으나 실제로는 **오름차순(ASC)**이다. 내림차순이면 4,3,5,2,1.

#### 소크라테스식 유도 과정 (Q&A 진행 기록)

| # | Claude의 질문 | 사용자 답변 | 판정 |
|---|---|---|---|
| Q1 | 20000과 20001 사이에 **정확히 무엇이 없어서** 못 넣는가? | "그 사이에 유효한 정수가 존재하지 않아" | ✅ 정답 |
| Q2 | 두 값 사이에 항상 또 다른 값이 있는 수 체계는? | "부동소수점을 활용하는건가?" | ◐ 방향 정답, 검증 필요 |
| Q3 | 부동소수점은 진짜로 그 조건을 만족하나? double은 몇 비트? | (스톨) | — |
| Q4 | 정수의 실패와 부동소수점의 실패는 같은 등급인가? | (스톨) | — |
| Q5 | 반씩 쪼갤 때 실제로 **늘어나는 것**은? | "길이가 길어지고 있네" | ✅ 정답 |
| Q6 | 무한 분할의 대가는? | (Q5와 통합) | ✅ |
| Q7 | 길이가 늘어나면서 정렬 가능한, 숫자가 아닌 자료형은? | "문자열로 하는건가" | ✅ 정답 |
| Q8 | `"a"`와 `"b"` 사이 값을 만들어보라 | (Claude가 시연으로 전환) | — |

Q3/Q4 정답: `double`은 **64비트 고정**(유효숫자 53비트). 20000~20001 사이는 약 **38회** 반분 후 `(a+b)/2 == a`가 된다. 그리고 이때 **예외를 던지지 않고** `a`와 같은 값을 조용히 반환한다. 결과적으로 두 행이 같은 `sr` 값을 갖게 되고 `ORDER BY`가 **비결정적**이 된다 — 화면상 "새로고침할 때마다 순서가 바뀌는" 재현 불가 버그.

> [!insight] 설계 리뷰의 핵심 기술
> "이 방안은 **언제** 죽는가"가 아니라 "이 방안은 **어떻게** 죽는가"를 묻는 것. 실패 확률이 같아도 fail-fast와 silent corruption은 전혀 다른 등급의 설계다.

#### 최종 답: Fractional Indexing

문자열은 **사전순(lexicographic)** 정렬되고, 뒤에 글자를 덧붙이면 원래 값보다는 크지만 다음 글자로 시작하는 값보다는 작다.

| 회차 | 앞 | 뒤 | 삽입값 |
|---|---|---|---|
| 1 | `a` | `b` | `an` |
| 2 | `a` | `an` | `ag` |
| 3 | `a` | `ag` | `ad` |
| 4 | `a` | `ad` | `ab` |
| 5 | `a` | `ab` | `aan` ← 글자 추가 |
| ... | | | 영원히 계속 |

이름: **Fractional Indexing**(Figma), **LexoRank**(Atlassian Jira).

> [!insight] 그릇을 바꾸면 대가가 사라진다
> 숫자에서 "길이가 늘어남"은 자료형과 싸우는 일이었다(고정 폭 초과, JSON에서 double로 강등). 문자열에서는 그게 자료형의 **기본 성질**이다. 같은 아이디어인데 **담는 그릇을 바꾸니 대가가 공짜가 됐다.**

#### 가변 정밀도 소수(BigDecimal/NUMERIC)를 안 쓰는 이유

작동은 한다. 그런데 JSON 경계에서 죽는다 — JavaScript의 `Number`는 IEEE 754 double이라 `0.10000000000000000000000000001`이 `0.1`로 조용히 뭉개진다. 서버와 DB가 아무리 정밀해도 API 경계에서 강등된다.

#### 사용자 케이스에 대한 최종 권고

**커리큘럼당 최대 100개면 방안 2(전체 재작성)를 권장.** Fractional Indexing이 압도적으로 유리해지는 건 **여러 명이 동시에 같은 목록을 드래그하는** 상황이다(각자 다른 1행만 건드리므로 충돌이 잘 안 남 — Figma가 쓰는 이유). 강사 한 명이 자기 커리큘럼을 편집하는 화면이라면 방안 2로 시작하고 필요해지면 갈아타는 게 맞다.
