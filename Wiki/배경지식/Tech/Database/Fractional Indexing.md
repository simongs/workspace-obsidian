## 정의

**Fractional Indexing**은 목록의 순서를 **사전순 정렬되는 문자열 키**로 표현해, 항목을 중간에 삽입할 때 **다른 행을 전혀 건드리지 않고 1행만 UPDATE**하는 기법이다.

Atlassian Jira에서는 **LexoRank**라는 이름으로, Figma에서는 실시간 협업 편집기의 순서 관리 방식으로 알려져 있다.

## 해결하는 문제

드래그 앤 드롭으로 순서를 바꾸는 목록(커리큘럼의 수업, 칸반 카드, 백로그 이슈)에서 **"중간에 끼워넣기"** 를 어떻게 저장하는가.

> [!example] 문제 상황
> 수업 5개가 `1,2,3,4,5` 순서. 5번을 드래그해 2와 3 사이에 놓으면 `1,2,5,3,4`가 되어야 한다.
> 순차 정수로 저장했다면 3, 4, 5의 순서값을 전부 다시 써야 한다.

## 접근법의 진화

> [!example] 왜 문자열까지 왔는가
> `정수 순차 (1,2,3)` → 중간 삽입 시 O(N) 재배치
> ↓ 간격을 벌리자
> `정수 희소 (10000, 20000...)` → 약 13회 후 고갈. 단 **명시적 실패**(감지 가능)
> ↓ 더 조밀한 수로
> `부동소수점` → 약 38회 후 고갈. **조용한 실패**(더 나쁨)
> ↓ 가변 정밀도로
> `BigDecimal / NUMERIC` → 사실상 무한. 단 **JSON 경계에서 double로 강등**
> ↓ 그릇을 바꾸자
> `문자열 사전순` → 무한, JSON 안전, 1행 UPDATE ★

### 각 단계가 죽는 지점

| 방식 | 한계 | 실패 방식 |
|---|---|---|
| 정수 희소 (간격 10000) | `log2(10000) ≈ 13`회 | 삽입 불가를 **감지 가능** → 예외/리밸런싱 |
| `double` (64비트, 유효숫자 53비트) | 약 38회 | `(a+b)/2 == a` 를 **예외 없이 반환**. 두 행이 같은 값 → `ORDER BY` 비결정적 |
| `NUMERIC` / `BigDecimal` | 사실상 없음 | JSON 직렬화 시 JS `Number`(=IEEE 754 double)로 **정밀도 유실** |

> [!warning] 부동소수점의 조용한 실패
> 정밀도 한계에 닿아도 예외가 안 난다. 두 행이 같은 정렬값을 갖고, 화면에는 **"새로고침할 때마다 순서가 바뀌는"** 재현 불가 버그로 나타난다.
> 정수 방식이 "못 넣습니다" 하고 즉시 터지는 것과는 **등급이 다른 실패**다.

## 핵심 원리

정수 집합은 **조밀(dense)하지 않다** — `n`과 `n+1` 사이는 텅 비어 있다. 그래서 정수로 순서를 표현하면 삽입 가능 횟수에 상한이 생기는 것이 필연이다.

문자열은 **사전순(lexicographic)** 으로 정렬되고, 뒤에 글자를 덧붙이면 **원래 값보다는 크지만 다음 글자로 시작하는 값보다는 작다**.

`"a"  <  "aa"  <  "ab"  <  "an"  <  "az"  <  "b"`

`"a"`에 무엇을 붙여도 `"b"`를 넘지 못한다. 따라서 쪼갤 게 없어지면 **글자를 하나 더 붙이면 되고**, 문자열은 길이 제한이 없으므로 이 과정에 끝이 없다.

| 회차 | 앞 | 뒤 | 삽입값 |
|---|---|---|---|
| 1 | `a` | `b` | `an` |
| 2 | `a` | `an` | `ag` |
| 3 | `a` | `ag` | `ad` |
| 4 | `a` | `ad` | `ab` |
| 5 | `a` | `ab` | `aan` ← 글자 추가 |
| … | | | 영원히 계속 |

> [!insight] 그릇을 바꾸면 대가가 사라진다
> 무한 분할의 대가는 **값의 길이가 늘어나는 것**이다. 숫자 타입에서는 이게 자료형과 싸우는 일이었다(고정 폭 초과, JSON 강등). 문자열에서는 그게 **자료형의 기본 성질**이다.
> 좋은 설계는 대개 이렇게 생겼다 — 문제를 푸는 게 아니라, **그 문제가 문제가 아닌 영역으로 옮기는 것**.

> [!info] 정보 이론적 배경
> "N번 삽입한 순서 상태"를 구별하려면 최소 N에 비례하는 정보량이 필요하다. 따라서 **고정 크기 필드로 무제한 삽입을 지원하는 것은 원리적으로 불가능**하다 — 어떤 인코딩을 써도. 이 문제는 "더 좋은 알고리즘 찾기"가 아니라 **"어떤 대가를 치를지 고르기"** 다.

## 스키마와 구현

```sql
CREATE TABLE lesson (
    id            BIGINT PRIMARY KEY,
    curriculum_id BIGINT NOT NULL,
    sort_key      VARCHAR(64) NOT NULL,   -- 'a0', 'an', 'aan' ...
    CONSTRAINT uk_lesson_order UNIQUE (curriculum_id, sort_key)
);

SELECT * FROM lesson WHERE curriculum_id = ? ORDER BY sort_key;
```

```kotlin
fun moveLesson(lessonId: Long, prevId: Long?, nextId: Long?) {
    val prevKey = prevId?.let { lessonRepo.findKey(it) }
    val nextKey = nextId?.let { lessonRepo.findKey(it) }
    val newKey = FractionalIndex.between(prevKey, nextKey)  // "a", "b" -> "an"
    lessonRepo.updateSortKey(lessonId, newKey)              // 1 row
}
```

FE는 전체 배열이 아니라 **"어느 항목 뒤, 어느 항목 앞"이라는 이웃 정보만** 보내면 된다.

## 직접 구현 시 함정

> [!warning] 최소 문자로 끝나는 키를 만들지 말 것
> `"a"`와 `"aa"` 사이에는 아무것도 넣을 수 없다.
> - `"a"`보다 크려면 → `"a"`로 시작하고 뒤에 뭔가 붙어야 함
> - `"aa"`보다 작으려면 → 두 번째 글자가 `'a'`보다 작아야 함
> - 알파벳 `a~z`에서 `'a'`보다 작은 글자는 **없음** → 삽입 불가
>
> 실제 구현들은 **"키가 알파벳 최소 문자로 끝나면 안 된다"** 는 불변식을 강제한다. 이런 엣지 케이스가 몇 개 더 있으므로 **검증된 라이브러리 사용을 권장**한다 (npm `fractional-indexing`, `lexorank`).

## 대안과의 선택 기준

| 방식 | 이동 비용 | 정렬 쿼리 | 실패 모드 | 적합 조건 |
|---|---|---|---|---|
| **전체 재작성** (`1..N` 재부여) | O(N) | ✅ 자명 | lost update | **항목 수 적음(~100), 단독 편집** |
| **링크드 리스트** (prev/next) | O(1) | ❌ 불가 | 체인 파손·사이클 | RDB에는 부적합 |
| **정수 희소 + 리밸런싱** | O(1) | ✅ | 주기적 재배치 필요 | 중간 규모 |
| **Fractional Indexing** | O(1) | ✅ | 키 길이 증가 | **동시 편집, 대량, 오프라인 편집** |

> [!important] 과잉 설계 주의
> 항목이 100개 수준이고 **한 사람이 단독으로 편집**하는 화면이라면 **전체 재작성이 더 나은 선택**이다. 불변식이 자명하고 디버깅이 쉽다(`aan` 같은 값은 눈으로 해석이 안 된다).
> Fractional Indexing이 압도적으로 유리해지는 건 **여러 명이 동시에 같은 목록을 드래그하는** 상황이다. 전체 재작성은 나중 요청이 앞 요청을 통째로 덮어쓰지만, Fractional Indexing은 각자 다른 1행만 건드리므로 **충돌 자체가 잘 나지 않는다**. Figma가 이 방식을 쓰는 이유다.

> [!failure] 링크드 리스트에 대한 흔한 오해
> "중간 이동 시 뒤 항목들이 연쇄 업데이트된다"는 것은 **배열 사고**다. 링크드 리스트는 `2.next`, `5.next`, `4.next` **3행만** 바뀌며 O(1)이다.
> 진짜 문제는 다른 데 있다 — RDB에서 `ORDER BY`로 순서를 못 뽑고, `LIMIT/OFFSET` 페이징이 불가능하며, 포인터 하나만 틀려도 목록 전체가 붕괴한다.
