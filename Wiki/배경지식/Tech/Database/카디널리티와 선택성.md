## 정의

ERD의 관계 표기(`1 ---- 0..1` 등)는 **하나의 숫자가 아니라 두 축의 정보**를 동시에 담는다.

| 축 | 읽는 값 | 결정하는 것 |
|---|---|---|
| **최대 카디널리티** | `1` vs `N` | 관계의 **유형** (1:1 / 1:N / N:M) |
| **최소 카디널리티 (선택성)** | `0` vs `1` | 참여의 **필수/선택** (optionality) |

이 둘을 구분하지 못하면 "필수 조건이니까 1:1 아닌가?" 같은 혼동이 생긴다.

## 읽는 규칙

> [!important] 카디널리티 읽는 법
> "내가 선 쪽 개체 **하나**를 기준으로, 반대편 개체가 **몇 개** 붙는가" — 그 답을 **반대편 끝**에 적는다.

## 예시: Member ↔ Instructor

> [!example] 회원은 강사가 될 수도 있다
> `Member  1 ──────── 0..1  Instructor`
>
> - **Instructor → Member**: 강사 한 명은 회원 **정확히 1명** → `1` (강사가 되려면 회원 필수)
> - **Member → Instructor**: 회원 한 명은 강사일 수도(1) 아닐 수도(0) → `0..1`

최대값만 보면 `1 : 1` — **이건 일대일 관계가 맞다**. `0..1`은 그걸 부정하는 게 아니라 **선택성 정보를 하나 더 얹은 것**이다.

> [!warning] `1 ---- 1` 이면 무슨 뜻인가
> "**모든** 회원은 반드시 강사이고, 모든 강사는 반드시 회원이다."
> 이러면 두 개체를 분리할 이유가 없다 — 테이블 하나로 합치면 된다.
> **개체를 나눴다는 것 자체가 "강사가 아닌 회원이 존재한다"는 선언이다.**

## 흔한 오해

> [!failure] "필수"라는 단어의 함정
> "A가 되려면 B가 필수"는 **A 입장에서의 필수**일 뿐이다. B 입장에서 A가 필수라는 뜻이 전혀 아니다.
> 필수 조건은 **방향이 있는 진술**인데 카디널리티는 양방향을 동시에 적으니 섞인다.

> [!failure] 카디널리티는 통계가 아니다
> "회원 1만 명 중 강사는 50명"이라는 **비율 정보는 다이어그램에 담기지 않는다.**
> 담기는 건 오직 "아무 회원이나 한 명 집었을 때 강사 레코드가 몇 개 딸려 오는가"뿐이다.
> **전체 집합의 시점이 아니라 인스턴스 하나의 시점**으로 봐야 한다.

## 구현: FK를 어디에 둘 것인가

**답은 필수(`1`)인 쪽**, 즉 Instructor다.

```sql
CREATE TABLE member (
    id       BIGINT PRIMARY KEY AUTO_INCREMENT,
    email    VARCHAR(255) NOT NULL UNIQUE,
    ...
);

CREATE TABLE instructor (
    member_id  BIGINT PRIMARY KEY,          -- PK이자 FK (식별 관계)
    bio        TEXT,
    CONSTRAINT fk_instructor_member
        FOREIGN KEY (member_id) REFERENCES member(id)
);
```

`member_id`를 Instructor의 PK로 그대로 쓰면 **한 줄의 PK 선언이 `1 ---- 0..1` 전부를 표현한다**:

| 선언 효과 | 보장되는 카디널리티 |
|---|---|
| PK = FK | "강사는 반드시 회원" (`1`) — DB 제약으로 강제 |
| PK는 유일 | "회원당 강사 레코드 최대 1개" (`..1`) — 별도 UNIQUE 불필요 |
| Instructor 행 없음 | "그 회원은 강사가 아님" (`0`) — 별도 플래그 컬럼 불필요 |

Instructor 입장에서 `member_id`는 외부에서 온 의미 있는 식별자이므로 [[Natural Key와 Surrogate Key|자연키]] 성격을 띤다.

## JPA 매핑

```kotlin
@Entity
class Instructor(
    @Id
    val memberId: Long? = null,

    @MapsId                          // PK를 FK와 공유
    @OneToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "member_id")
    val member: Member,              // non-null = 필수(1)

    val bio: String? = null,
)

@Entity
class Member(
    @Id @GeneratedValue val id: Long? = null,
    val email: String,

    @OneToOne(mappedBy = "member", fetch = FetchType.LAZY)
    val instructor: Instructor? = null,   // nullable = 선택(0..1)
)
```

> [!insight] 널 가능성이 카디널리티와 1:1로 대응한다
> `member: Member`(non-null)가 다이어그램의 `1`, `instructor: Instructor?`(nullable)가 `0..1`이다.
> Kotlin의 타입 시스템이 ERD를 그대로 받아 적는 셈이다. → [[Null Safety]]

## 1:1 관계의 존재 이유

실무에서 순수한 `1..1 : 1..1`은 거의 없다. 1:1로 테이블을 나누는 이유는 대개 셋 중 하나다:

1. **선택적 확장** — 일부 행만 갖는 속성 (Member ↔ Instructor)
2. **컬럼 수·조회 빈도 분리** — 성능
3. **접근 권한 분리** — 민감정보 테이블 격리
